# Vercel + Supabase: manual-sync pilot

This deployment uses the existing Vercel root `aynor-onboarding-frontend/source`. All function code and its runtime dependencies are inside that directory. `api/handler.js` is a Node function; `vercel.json` routes `/api/*` to it and preserves SPA deep links. No SQLite, local disk, persistent worker, SSE server or background jobs are used by this path. The older SQLite/Render/local path remains available independently.

## Activation, one step at a time

1. Run `supabase/migrations/202610270001_aynor_foundation.sql` in Supabase SQL Editor. This was the first setup script.
2. Run `supabase/migrations/202610270002_serverless_operations.sql`. Expected result: **AYNOR serverless setup complete**. It adds backend-only atomic operations and sync leases; it does not remove existing records. Run the complete file, not a selected fragment.
3. In Vercel's Production environment, keep `SUPABASE_URL` as the bare project HTTPS address and `SUPABASE_SECRET_KEY` as a Secret. Never use the publishable key in that variable. No database connection string, IPv4 add-on, paid persistent disk or Render account is needed.
4. Add `INITIAL_OWNER_EMAIL` (your email) and `INITIAL_OWNER_PASSWORD` (a new private strong password, 16–200 characters) as server variables. Make the password Secret. This operator-provisions the existing owner identity independently of public signup. An existing account/password is never overwritten. New public accounts use Supabase Auth email confirmation as described below.
5. Keep `VITE_API_MODE=server` as Config in Production. Vercel builds also detect the platform through its system environment and automatically use the API, so a missing/mistyped mode value cannot silently choose demo accounts. Local development still defaults to the offline prototype unless explicitly enabled. The HTML exporter always forces offline mode, even on Vercel. Never give credentials a `VITE_` prefix.
6. Redeploy the latest tested `main` revision. Keep Root Directory `aynor-onboarding-frontend/source`, Vite preset and output `dist`. Vercel reads `vercel.json` from that root. Node 24.x is declared in its package. Do not change the root to the repository root.
7. Visit `/api/health` on the actual deployment. Expected JSON: `{"status":"ok","storage":"supabase","syncMode":"manual"}`. Then visit `/auth/login`, sign in using the owner credentials, and create a workspace. The health check needs the second setup script and the correct server secret but does not reveal those values.
8. Test a non-sensitive published CSV sheet first. Map date/revenue/expenses and save. Mapping performs the first read within the request; subsequent changes require **Sync now**. Reports persist across function cold starts and browser reloads.
9. Once sign-in works and the password is saved in a password manager, remove **both** `INITIAL_OWNER_EMAIL` and `INITIAL_OWNER_PASSWORD` and redeploy. The stored account remains. Password recovery email is not implemented; retain that password securely.

Do not share secrets in screenshots/chat. The SQL files contain no credentials and can be shared. Missing setup/config produces an explicit error; it never silently changes to demo financial data.

## Account signup and logout

Public signup is available at `/auth/signup`; login links to it and signup links back to login. New registrations are handled by the existing Supabase project's Auth service, not browser mock data. Email confirmation must succeed before an app account/session and company access are provisioned. The existing owner and other legacy scrypt accounts continue to sign in through their existing credentials. New accounts use a `supabase:<provider UUID>` identity marker in the app password column, and Supabase remains authoritative for their password checks. No new database migration or Vercel variable is required.

Production activation requires these **Supabase Authentication settings**:

1. Enable the Email provider and new user signups. Keep **Confirm email** enabled.
2. Under **URL Configuration**, set Site URL to `https://aynor.vercel.app` and add `https://aynor.vercel.app/auth/confirmed` to Redirect URLs. Confirmation links must return to the actual production domain.
3. Configure **custom SMTP** under the Authentication email settings to deliver to arbitrary user addresses. Supabase's built-in sender restricts delivery to project-team addresses and has low email rate limits; it is not a general delivery service. Sender verification and SMTP credentials belong in Supabase, never in browser code or chat. The application cannot create/configure the operator's mail-provider account from this workspace.

The browser asks users to check their inbox and sign in after following the confirmation link. Resend has a visible cooldown; server-side IP/email limits and provider limits also apply. Unconfirmed sign-in is denied. Provider credentials, tokens and diagnostic bodies are never returned. Confirmation redirects remove hash tokens from the URL; the app establishes its own HttpOnly Secure SameSite=Lax session only after checking the confirmed identity with Supabase. Default-sender restrictions, disabled signup, temporary delivery failure and rate limits have explicit errors rather than fake verification success.

**Log out** is visible below the desktop sidebar account section and in the header profile dialog (including mobile); the company-list header also exposes logout. Logout revokes the current native session, expires its cookie, clears session drafts and notifies other tabs. Failed requests keep the current screen/account and allow retry. Logout is idempotent for an expired/already-revoked session. It does not revoke sessions on other devices. Signing up with another email creates no membership in the previous account's companies. Existing owner workspaces remain intact.

The account browser test covers logout across tabs, signup, denial before confirmation, controlled provider confirmation, isolated workspace creation, mobile logout access, retry after a failed logout, and returning to the original owner. Tests use a local email-provider fixture; actual SMTP delivery and Supabase URL/provider settings still require the operator's live setup.

## Customer journey and onboarding routing

Public signup and provider-backed login explicitly check Supabase Auth settings and fail closed unless `mailer_autoconfirm` is false. Turning off Confirm email cannot silently enable automatic account verification. Provider login still requires a confirmed email identity matching the requested address; neither a clicked callback URL nor a browser-supplied flag creates an app session. Existing operator-provisioned legacy owner identities retain their established login path; they are not public self-registration accounts.

Duplicate-account errors offer sign-in and confirmation-resend actions. Unconfirmed login offers a direct path to resend. Confirmation email can be entered on a different browser/device without having to sign up again. Cooldown is based on the last actual send, rather than restarting for every visit. Expired callback errors are displayed and URL token/query secrets are removed. User-facing temporary errors do not expose provider setup instructions; server diagnostics retain actionable configuration errors.

Login returns an authorized destination computed from current membership and saved company progress. No company leads to Company Details. An unfinished owned/administered workspace resumes its saved onboarding step, including when a dashboard `next` link was supplied. Completed workspaces open their requested page/dashboard. Invited scoped members open the dashboard rather than an onboarding page they cannot edit. Unrecognized/unauthorized company destinations fall back to an accessible workspace; external redirects are rejected. The entry page uses the same pure resolver. A direct unfinished completion URL returns to Review.

At least one department is required to continue. Data import/mapping must either produce a valid snapshot or be explicitly skipped; Continue cannot mark an empty import as completed. Explicitly skipping an unconnected data source also marks its dependent mapping step skipped and proceeds to priorities, avoiding a repeated connector screen. The mapping review displays saved column mappings instead of a fresh empty connector. Review saves completion before opening the completion screen. Explicit Save & finish later still permits inspecting an incomplete dashboard; the next login resumes onboarding. Skipped data produces an honest data-pending completion state and actionable empty dashboard, rather than invented metrics. Logout is accessible from onboarding as well as the desktop/mobile dashboard.

Successful source mutations immediately publish their returned status to company-scoped UI listeners. Pending older reads cannot overwrite that status. Hosted dashboards initially show All available records for validated sources, including current-month Google data; users can still select a complete-month reporting period.

`tests/customer-journey.browser.mjs` exercises the complete rendered path: signup, unconfirmed denial, expired/invented callback denial, controlled email confirmation, company creation, required departments, logout/login with a dashboard next link resuming the saved step, reload, real CSV upload/mapping, saved mapping review, explicit optional skips, final review, persisted current-month dashboard metrics and logout/login to the completed dashboard. It supplements the independent private Google, Excel/URL, account-isolation and manual-sync browser journeys. These are controlled-provider tests, not a claim that all live external-service behavior is issue-free.

## Private sheets

Public CSV needs no Google OAuth credentials. Private sheets additionally need server-only `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` and stable `SHEETS_ENCRYPTION_KEY` (64 hexadecimal characters). Register the callback on the actual production domain: `https://YOUR-DOMAIN/api/integrations/google/callback`. The browser must stay on that same hostname through consent so its session cookie returns. Configure Google consent test users and enable Sheets API.

Only spreadsheet read scope is requested. OAuth state is hashed, user/company-bound, expiring and consumed once. Stored tokens use AES-256-GCM; refresh uses a credential compare-and-swap so another connection cannot be overwritten. Google errors do not expire the app session. No key or source credential is returned by the API.

**Connect Google** is always actionable. When credentials are missing it opens a setup guide, with safe variable-name diagnostics and the callback address for the current domain. An optional browser-generated encryption key is copied directly to the clipboard, never sent to analytics, rendered, or stored in browser storage. Paste it only into the server-only Vercel Secret and retain that value across deployments. The app cannot create a Google Cloud project or provision OAuth credentials in the operator's account.

One-time Google setup:

1. Open [Google Sheets API](https://console.cloud.google.com/apis/library/sheets.googleapis.com), select/create an Aynor project and enable the API.
2. In Google Auth Platform, set up branding/contact details and an External audience. Under Data Access add `https://www.googleapis.com/auth/spreadsheets.readonly`. While the app is in Testing, add the Google account that has access to your sheet as a test user. Testing-mode grants can expire; publishing/verification is a separate Google-controlled requirement before a wider release.
3. Create a **Web application** OAuth client. Register `https://aynor.vercel.app/api/integrations/google/callback` as the Authorized redirect URI for this production deployment.
4. Save that client's ID and secret under `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in Vercel Production. Save the exact callback under `GOOGLE_REDIRECT_URI` and a stable random 64-hex-character secret under `SHEETS_ENCRYPTION_KEY`. All are server variables, never `VITE_*`. Redeploy.
5. Sign in on `https://aynor.vercel.app`, choose Private sheet, paste your sheet link and choose **Connect Google & read columns**. Grant read-only permission using the account that can open the sheet.

Authorization returns to the originating onboarding integrations/mapping screen, or Connections settings, using a fixed destination bound into the one-use state. A pasted link is retained in company-scoped session storage during the redirect. Choosing the combined connect/read action reads the columns on return. Cancellation preserves the prior source and keeps the link available for retry. A `gid` in the pasted link selects that tab. A preview-domain session cannot initiate consent using a different production callback domain; use the actual production hostname.

## Spreadsheet import tabs

The hosted import UI has **Connect Google**, **Upload sheet**, and **Paste URL** tabs in both onboarding and Connections settings. Existing private Google consent and manual sync remain available.

**Upload sheet** accepts Excel `.xlsx` and UTF-8 comma-separated `.csv` files up to 5 MB. Older `.xls` workbooks must be saved as `.xlsx` first. A maintained Excel parser runs in a Web Worker, with a 20-second timeout and no formula execution. Excel date cells become ISO dates; formulas use the workbook's saved/cached results. The operator can choose a worksheet and header row, review the preview, edit the three financial mappings and confirm import. Workbooks can contain up to 50 worksheets; each imported dataset supports 52 columns, 10,000 records and a 3 MB normalized JSON request. The default header suggestion examines the first 20 rows; the selector exposes the first 100 rows.

The upload API validates every record **before** replacing a source. Preview requests do not change the current source. The existing backend-only configure/claim/publish operations persist the mapping and normalized reporting snapshot with a generation/lease check. Original files and unmapped raw cell contents are not stored. Uploaded reports survive new function instances and page reloads. This uses the existing SQL setup—no migration, bucket, OAuth credentials or new environment variable is required for file uploads. Uploaded files are snapshots; **Upload new version** updates the report rather than implying that a local file can sync automatically. The hosted financial report defaults to **All available records** for validated sources, including records in the current month.

**Paste URL** accepts published Google CSV links and ordinary Google Sheets links shared for viewing; `gid` selects the tab. Outbound requests remain restricted to Google spreadsheet endpoints and allowed Google content redirects. Private/sign-in-required URLs are directed to Connect Google. UI URL previews preserve the current saved report until mapping is confirmed. Validation errors preserve existing saved data. A workspace currently has one active financial reporting source; confirming a new import replaces that source.

`npm run test:serverless` includes real `.xlsx` bytes with multiple worksheets, a title row, a styled Excel date and a cached formula, then verifies mapping, current-month totals, reload persistence, rejected replacement retention, CSV replacement, shared-URL import, and phone/tablet/wide layouts. Google provider responses remain controlled test fixtures, not a claim of a new live cloud test.

## Consistency and access

The HTTPS adapter uses the Supabase server secret in `apikey`. Modern `sb_secret_` keys are not treated as JWT bearer tokens. All data access is server-side. Browser roles have no table or RPC privileges; service-role SQL functions are SECURITY INVOKER and explicitly deny PUBLIC/anon/authenticated execution. The API must authenticate the user and pass the trusted actor ID. Database-side membership checks protect atomic mutations; company-wide financial reports are Owner/Admin only.

Company creation, owner membership, audit and idempotency results commit together. Workspace/profile changes check a locked current version. Permission changes reject ownership changes and invalid scopes. Invitation acceptance checks identity/expiry/status atomically. Public email signup uses Supabase Auth. App invitations are not automatically created, and outbound invitation email and password recovery remain separate unfinished features.

Each manual sync claims a durable PostgreSQL lease. Another function cannot claim an active sync. Lease expiry allows recovery after a function is terminated. Source generation and lease IDs guard publication, so removed/remapped sources cannot be overwritten by old requests. Source changes invalidate old snapshots atomically. Failed validation/provider reads retain the last valid snapshot. Company membership is checked again on publication. There is no fire-and-forget work after the function responds.

The browser refreshes connection status and immediately reloads after a local mutation. It opens no SSE stream in manual mode. A database error, revoked provider token, active sync, cooldown, missing mapping and empty reporting period all have explicit UI/API responses. Source freshness older than one day is labeled stale; it is not a promise of automatic polling of Google.

Input/size/date/currency rules match the local live slice: ISO dates, numeric amounts in the workspace currency, 52 columns, 10,000 rows, 5 MB, integer-minor-unit sums, complete UTC calendar reporting periods, and no fabricated comparisons. The function has a 60-second maximum; individual upstream reads time out sooner. Long requests that are terminated before publishing keep the last snapshot; retry after the lease expires (two minutes).

## Limits and migration

This changes the application's storage path; it does **not** automatically import old SQLite files or browser prototype state. Those remain untouched. The current Supabase project was initialized empty. Existing real SQLite data needs a separate deliberate export/import with ownership checks before switching a populated deployment.

The live financial Overview is connected. The other intelligence modules retain their documented integration limits; AI, actions and goal-tracking metadata are not magically promoted to production persistence. Email signup can create separate workspaces after provider-confirmed email ownership; this remains an MVP with the reporting and recovery limits described here. Free-provider quotas and plan eligibility still apply; manual sync avoids a paid always-on worker but is not an unlimited hosting guarantee.

### Flexible table imports

Hosted imports now have two explicit report modes. Existing financial imports keep their date/revenue/expenses aggregation and current contracts. The new **Explore my table** mode imports arbitrary rectangular tables without assigning financial meanings. Google inspection reads the first 100 rows for header/type suggestions, lists all grid tabs, and permits a header-row override. Empty tabs can be switched without losing access to the tab picker. Excel uses the same header suggestion. Column types are suggested from samples, then editable as text, number, currency, percentage, date, boolean, or excluded. Ambiguous non-year-first dates remain text until the user chooses Date and an explicit day-first/month-first format. Optional last-data-row selection excludes footnotes/totals. Blank cells remain null; every retained typed value is checked on the server before replacing the current source.

`POST /companies/:id/sheets/tables` uses the existing Owner/Admin membership checks, source-generation lease and snapshot RPCs. No migration, new credential, authentication change or external AI service is required. It validates all selected tables before source replacement, stores only normalized retained columns, and supports up to 10 selected tabs, 10,000 data records per tab, 52 columns per tab and 3 MB total normalized snapshot. Upload requests also have a 3 MB JSON body limit; files remain subject to the existing 5 MB browser limit. Header rows are within the first 100 rows. This supports one rectangular table per worksheet, not arbitrary pivot/cross-tab layouts, multiple separate tables on a single worksheet, merged-cell reconstruction or arbitrary date/number locales. Unsupported values can remain text without corrupting the source.

Private Google and Excel can import multiple tabs in one batch. A published/shared CSV URL contains one selected tab; use Google OAuth or a workbook for multiple tabs. Google table refresh re-reads all selected tabs using their saved header/range/type choices. Sync remains manual. Excel imports remain saved snapshots and require a new upload to refresh. Changing a Google tab's schema can require reinspection; the last successful snapshot is retained on sync validation failure. There is still **one active source/report mode per workspace**: a new confirmed import replaces it. Switching report mode does not convert testing/project data into financial metrics.

Generic snapshots now retain the actual imported nonfinancial records (not only financial aggregates) in the existing server-only, company-scoped snapshot table. Ignored columns are excluded. Only existing Owner/Admin report access is enabled. The Overview renders table tabs, record/column counts, completeness, top category counts, searchable paginated records and confirmed relationships. It does not infer KPIs or sum arbitrary numeric identifiers. All data is bounded; no spreadsheet formulas or cell HTML are executed.

For multi-tab imports, shared ID/code/email column names generate optional connection suggestions. Only explicitly checked connections are stored. The backend requires compatible column types, actual matching values and a unique reference key, preventing many-to-many duplication. Connections display in Overview and reference-table rows navigate to filtered related records. No financial totals are combined across tables. Names that differ or nonidentifier relationships are not auto-inferred.

Validation: `tests/table-data.test.js` covers locale ambiguity, header/range selection, physical error-row numbering, real PostgreSQL persistence, invalid replacement retention, Google re-sync, and unique-key relationship rules. `tests/tables.browser.mjs` covers an actual multi-tab Excel import through onboarding and the table dashboard, including explicit dates, confirmed links, related-record navigation, search, pagination, reload and responsive layouts. Existing financial/authentication browser journeys remain in `npm run test:serverless`. Provider interactions use controlled fixtures, not live customer Google accounts.
